Tema de la sesión

Testing de APIs con Pytest

1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz será capaz de escribir pruebas automatizadas de su API con Pytest: montar una base de datos de prueba aislada mediante fixtures, sustituir dependencias con dependency_overrides, simular servicios externos sin llamarlos de verdad, y verificar tanto los casos correctos como los errores de negocio.

2. Qué se prueba en una API y con qué herramientas

Pieza

Función

Pytest

Ejecutor de las pruebas. Descubre los archivos test_*.py y las funciones test_*.

Fixture

Función decorada con @pytest.fixture que prepara algo y lo entrega a la prueba. Con yield, lo que va después limpia.

TestClient

Cliente que llama a la aplicación en memoria, sin levantar uvicorn ni abrir un puerto.

dependency_overrides

Diccionario de la aplicación que permite sustituir cualquier dependencia durante las pruebas.

Base de prueba

SQLite en memoria, creada y destruida en cada prueba. Nunca se prueba contra la base de desarrollo.

Doble de prueba

Sustituto de un servicio externo. Evita llamadas reales, costes y resultados que cambian.

Idea clave

Las dependencias que se introdujeron el 27 de agosto se cobran hoy. Como la sesión de base de datos, el usuario autenticado y el modelo de IA entran por Depends, cada uno puede sustituirse en las pruebas sin tocar una sola línea del código de producción. Una API que obtiene sus recursos por su cuenta, sin dependencias, es una API que no se puede probar.

4. Ejemplo detallado: explicación línea por línea

N°

Elemento

Explicación

1

sqlite+aiosqlite:///:memory:

Base que vive en memoria y desaparece al terminar. No toca ningún archivo ni la base de desarrollo.

2

poolclass=StaticPool

Obliga a reutilizar una sola conexión. Sin esto, cada conexión abriría su propia base en memoria y las tablas creadas no serían visibles.

3

app.dependency_overrides[obtener_sesion]

Sustituye la dependencia en toda la aplicación. Ningún archivo de app/ se modifica para poder probar.

4

dependency_overrides.clear() al final

Sin la limpieza, la sustitución persiste y contamina las pruebas siguientes: el fallo aparece en otro archivo y despista.

5

TestClient sin gestor de contexto

No ejecuta el lifespan, así que no se crea la base real, ni se carga joblib, ni se abre el cliente HTTP. Cada prueba declara lo que necesita.

6

Datos de prueba en la fixture

Cada prueba arranca con el mismo catálogo conocido. Depender de los datos de desarrollo produce pruebas que fallan cuando alguien los edita.

7

_token(cliente, documento)

Se obtiene un token real llamando al endpoint de login: se prueba también el flujo de autenticación, no solo se lo salta.

8

ModeloFalso

Doble del modelo: sin joblib, sin scikit-learn y sin el tiempo de carga. Se prueba el endpoint, no el modelo — este se evalúa con sus propias métricas.

9

predecir con tendencia realista

El doble reproduce la relación entre días y riesgo. Un doble que devolviera siempre 0.5 haría pasar la prueba sin comprobar nada útil.

10

httpx.MockTransport

Intercepta las peticiones del cliente sin salir a la red: ni coste, ni dependencia del proveedor, ni resultados distintos en cada ejecución.

11

monkeypatch.setattr(configuracion, …)

Ajusta la configuración solo durante la prueba; Pytest restaura el valor original al terminar.

12

@pytest.mark.parametrize

Una misma prueba con varias entradas. Cada caso aparece como una prueba distinta en el informe.

13

assert respuesta.status_code == 409 y el código de error

Se comprueba el código HTTP y el identificador del error. Solo el 409 no distingue entre «sin ejemplares» y «límite superado».

14

--cov=app --cov-report=term-missing

Informa qué porcentaje del código ejecutan las pruebas y qué líneas quedan sin cubrir. Es una guía, no una meta: cobertura alta con malas aserciones no prueba nada.

5. Errores comunes y cómo evitarlos

Probar contra la base de desarrollo: las pruebas borran datos reales y sus resultados dependen de lo que hubiera guardado.

Olvidar StaticPool con SQLite en memoria: aparece «no such table», porque cada conexión abre una base vacía distinta.

No limpiar dependency_overrides: la sustitución se filtra y una prueba posterior falla por un motivo que no está en su archivo.

Usar TestClient como gestor de contexto sin quererlo: se ejecuta el lifespan, se toca la base real y se cargan servicios que la prueba no necesita. A la inversa, si lo que se quiere probar es el lifespan, hay que usarlo con with.

Pruebas que dependen unas de otras: si test_b necesita que test_a haya corrido antes, ejecutar solo test_b falla. Cada prueba se prepara sola.

Llamar de verdad al proveedor externo en las pruebas: son lentas, cuestan dinero y fallan cuando el servicio está caído.

Probar solo el camino feliz: los errores de negocio —409, 404, 422— son justamente lo que se rompe al refactorizar.

Comprobar únicamente el código de estado: dos reglas distintas pueden responder 409 y solo el código de error las distingue.

Perseguir el 100 % de cobertura: se acaban escribiendo pruebas sin aserciones útiles solo para tocar líneas.
