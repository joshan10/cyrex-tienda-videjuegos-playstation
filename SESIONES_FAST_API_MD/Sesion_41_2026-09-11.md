Tema de la sesión

Procesamiento en background (BackgroundTasks)

1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz será capaz de ejecutar trabajo después de haber respondido al cliente usando BackgroundTasks, distinguir qué operaciones son adecuadas para ese mecanismo y cuáles exigen una cola de tareas real, y garantizar que un fallo en segundo plano no rompa la operación principal ni pase inadvertido.

2. Trabajo que puede esperar

Registrar un préstamo son dos cosas: crear el registro —que el socio necesita confirmado ahora— y dejar constancia en la auditoría y avisar por correo —que puede ocurrir un segundo después sin que nadie lo note—. BackgroundTasks separa ambas: la respuesta sale en cuanto la parte esencial termina, y el resto se ejecuta después.

Concepto

Descripción

BackgroundTasks

Parámetro que FastAPI inyecta en el endpoint. Las funciones registradas se ejecutan después de enviar la respuesta.

add_task(fn, *args)

Registra la función y sus argumentos. No la ejecuta en ese momento: solo la encola.

Ámbito

Mismo proceso del servidor. Si el proceso se reinicia antes de ejecutarla, la tarea se pierde.

Sin reintentos

Si falla, no vuelve a intentarse. La excepción se registra pero el cliente ya recibió su respuesta.

Sin resultado

No hay forma de devolverle al cliente lo que produjo la tarea.

def o async def

Ambas valen. Una función síncrona se ejecuta en el pool de hilos; una asíncrona, en el bucle de eventos.

Idea clave

BackgroundTasks sirve para trabajo que puede perderse sin consecuencias graves. Si perder la tarea implica un cobro no registrado, un correo de confirmación que nunca llega o un dato que queda incoherente, hace falta una cola persistente —Celery, RQ, ARQ— con reintentos y almacenamiento propio. Elegir mal aquí produce fallos que no dejan rastro.

Adecuado para BackgroundTasks

Exige una cola real

Escribir una línea de auditoría

Cobrar una multa por retraso

Invalidar una caché

Generar y enviar una factura

Enviar una notificación informativa

Enviar el correo de restablecimiento de contraseña

Registrar una métrica de uso

Procesar un archivo de miles de registros

Actualizar un contador aproximado

Sincronizar con un sistema externo de forma garantizada

Equivalencia con Django REST Framework

En Django, cualquier trabajo posterior a la respuesta implicaba montar Celery con Redis o RabbitMQ desde el primer día, incluso para escribir una línea de log. FastAPI trae BackgroundTasks para el caso sencillo, sin infraestructura. La contrapartida es que no ofrece nada de lo que Celery sí da: persistencia, reintentos, programación y visibilidad del estado de la tarea. Es una herramienta más simple para un problema más pequeño, no un sustituto.

app/services/auditoria.py — nuevo archivo

"""Registro de auditoría. Se ejecuta en segundo plano, con su propia sesión."""

import logging

from app.core.base_datos import FabricaDeSesiones

from app.models.biblioteca import RegistroAuditoria

logger = logging.getLogger("biblioapi.auditoria")

async def registrar_evento(

 accion: str,

 recurso: str,

 recurso_id: int,

 autor_id: int | None = None,

 detalle: str | None = None,

) -> None:

 """Abre su propia sesión: la de la petición ya se cerró al responder."""

 try:

 async with FabricaDeSesiones() as sesion:

 sesion.add(

 RegistroAuditoria(

 accion=accion,

 recurso=recurso,

 recurso_id=recurso_id,

 autor_id=autor_id,

 detalle=detalle,

 )

 )

 await sesion.commit()

 except Exception:

 # Una tarea de fondo que lanza una excepción no llega a ningún cliente:

 # si no se registra aquí, el fallo desaparece sin dejar rastro.

 logger.exception("No se pudo registrar la auditoría de %s %s", accion, recurso_id)

app/routers/prestamos.py — el endpoint encola el trabajo posterior

from fastapi import BackgroundTasks

from app.services.auditoria import registrar_evento

from app.services.notificaciones import avisar_prestamo_registrado

@router.post(

 "",

 response_model=PrestamoRespuesta,

 status_code=status.HTTP_201_CREATED,

 summary="Registrar un préstamo",

)

async def registrar_prestamo(

 sesion: SesionDep,

 datos: PrestamoCrear,

 tareas: BackgroundTasks,

 bibliotecario: Bibliotecario,

):

 prestamo = await crud_prestamos.registrar(

 sesion,

 libro_id=datos.libro_id,

 socio_id=datos.socio_id,

 dias_prestamo=datos.dias_prestamo,

 )

 # A partir de aquí nada retrasa la respuesta: solo se encola.

 tareas.add_task(

 registrar_evento,

 accion="prestamo_registrado",

 recurso="prestamo",

 recurso_id=prestamo.id,

 autor_id=bibliotecario.id,

 detalle=(

 f"libro={prestamo.libro_id} socio={prestamo.socio_id} "

 f"vence={prestamo.fecha_devolucion_esperada}"

 ),

 )

 tareas.add_task(

 avisar_prestamo_registrado,

 email=prestamo.socio.email,

 titulo=prestamo.libro.titulo,

 fecha_devolucion=str(prestamo.fecha_devolucion_esperada),

 )

 return prestamo

@router.post(

 "/{prestamo_id}/devolucion",

 response_model=PrestamoRespuesta,

 summary="Registrar la devolución de un préstamo",

)

async def registrar_devolucion(

 sesion: SesionDep,

 prestamo_id: Annotated[int, Path(ge=1)],

 tareas: BackgroundTasks,

 bibliotecario: Bibliotecario,

):

 prestamo = await crud_prestamos.registrar_devolucion(sesion, prestamo_id)

 con_retraso = (

 prestamo.fecha_devolucion_real > prestamo.fecha_devolucion_esperada

 )

 tareas.add_task(

 registrar_evento,

 accion="devolucion_registrada",

 recurso="prestamo",

 recurso_id=prestamo.id,

 autor_id=bibliotecario.id,

 detalle=f"con_retraso={con_retraso}",

 )

 return prestamo

app/routers/auditoria.py — consultar lo que quedó registrado

from typing import Annotated

from fastapi import APIRouter, Query

from pydantic import BaseModel, ConfigDict

from sqlalchemy import select

from datetime import datetime

from app.dependencias import Bibliotecario, SesionDep

from app.models.biblioteca import RegistroAuditoria

router = APIRouter(prefix="/auditoria", tags=["Auditoría"])

class EventoRespuesta(BaseModel):

 model_config = ConfigDict(from_attributes=True)

 id: int

 momento: datetime

 accion: str

 recurso: str

 recurso_id: int

 autor_id: int | None

 detalle: str | None

@router.get("", response_model=list[EventoRespuesta], summary="Consultar la auditoría")

async def listar_eventos(

 sesion: SesionDep,

 bibliotecario: Bibliotecario,

 accion: Annotated[str | None, Query()] = None,

 limite: Annotated[int, Query(ge=1, le=100)] = 20,

):

 consulta = select(RegistroAuditoria)

 if accion is not None:

 consulta = consulta.where(RegistroAuditoria.accion == accion)

 resultado = await sesion.scalars(

 consulta.order_by(RegistroAuditoria.momento.desc()).limit(limite)

 )

 return list(resultado)

4. Ejemplo detallado: explicación línea por línea

N°

Elemento

Explicación

1

tareas: BackgroundTasks

Basta declararlo en la firma: FastAPI lo inyecta. No requiere Depends ni configuración.

2

tareas.add_task(fn, ...)

Registra la función y sus argumentos; se ejecuta después de enviar la respuesta. Escribir add_task(fn()) la ejecutaría en el acto, que es justo lo contrario.

3

Argumentos por nombre

add_task acepta posicionales y por nombre. Nombrarlos evita el error silencioso de invertir dos parámetros del mismo tipo.

4

Sesión propia en la tarea

La sesión de la petición se cierra al responder. Usarla dentro de la tarea produce «Instance is not bound to a Session» o un error de conexión cerrada.

5

async with FabricaDeSesiones()

La tarea abre y cierra su propia sesión, igual que hace la dependencia para la petición.

6

try/except con logger.exception

Una excepción en segundo plano no llega a ningún cliente. Sin este registro, el fallo es invisible.

7

prestamo.socio.email accedido en el endpoint

El dato se lee antes de encolar y se pasa como argumento. Pasar el objeto ORM a la tarea fallaría: su sesión ya no existe.

8

str(fecha_devolucion_esperada)

Los argumentos de la tarea se convierten a tipos simples. Así la función de notificación no depende del modelo ni de la sesión.

9

Orden de las tareas

Se ejecutan en el orden en que se registraron, una tras otra, no en paralelo.

10

Middleware y tareas

El middleware de logging mide solo hasta el envío de la respuesta: las líneas de las tareas aparecen después en la consola.

11

default=lambda: datetime.now(timezone.utc)

La marca de tiempo se calcula en Python al crear la fila, en UTC. Un default fijo se evaluaría una sola vez, al importar el módulo.

5. Errores comunes y cómo evitarlos

Escribir add_task(mi_funcion()) con paréntesis: se ejecuta de inmediato y se registra su resultado, que no es invocable. El error aparece después de responder, cuando ya nadie mira.

Reutilizar la sesión de la petición dentro de la tarea: al ejecutarse, esa sesión ya está cerrada.

Pasar objetos ORM como argumentos de la tarea: quedan desvinculados de su sesión y cualquier atributo perezoso falla.

No capturar las excepciones dentro de la tarea: el fallo no llega a ningún cliente y, sin log, desaparece por completo.

Usar BackgroundTasks para trabajo que no puede perderse —cobros, correos críticos, sincronizaciones—: un reinicio del servidor lo descarta sin aviso.

Meter trabajo pesado y prolongado en una tarea de fondo: sigue ocupando el mismo proceso que atiende las peticiones.

Registrar la tarea antes de que la operación principal haya tenido éxito: si el commit falla, se auditará un préstamo que no existe.

Esperar que la tarea devuelva algo al cliente: la respuesta ya se envió cuando la tarea empieza.
