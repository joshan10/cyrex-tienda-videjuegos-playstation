29

Manejo de errores

La regla de negocio lanza una excepción del dominio; un manejador registrado la traduce a código HTTP. El módulo crud no conoce HTTP. Todos los errores salen con el mismo formato.

30

Inyección de dependencias

Depends extrae lo repetido y puede cortar la petición. Una clase con __call__ permite configurar la misma dependencia de formas distintas. dependencies=[...] aplica a todo un router.

31

Middlewares, CORS y seguridad

El middleware envuelve toda petición; call_next marca la frontera entre entrada y salida. CORS es una restricción del navegador y exige lista explícita de orígenes.

Idea clave

Las tres sesiones separan responsabilidades por alcance: el middleware actúa sobre todas las peticiones, la dependencia sobre las que la declaran, y la excepción de dominio sobre una regla concreta. Cuando surja la duda de dónde poner algo, la pregunta es a cuántas peticiones debe afectar.

¿Por qué el módulo crud no debe lanzar HTTPException?

Porque acopla la regla de negocio al protocolo web. Esa misma función debe poder usarse desde una tarea programada o desde la consola.

2

Se necesita exigir un rol en los seis endpoints de un recurso. ¿Dónde va?

En dependencies=[...] del APIRouter, no repetida en cada firma.

3

¿Qué diferencia hay entre declarar Depends en la firma y en dependencies=[...]?

La firma inyecta el resultado; dependencies solo la ejecuta para que valide o corte.

4

Una regla debe aplicarse también a las peticiones que terminan en 404 de ruta inexistente. ¿Dependencia o middleware?

Middleware: la dependencia solo corre si la ruta existe y la declara.

5

¿Por qué la API responde bien en Postman y falla desde el navegador?

Casi siempre CORS: el origen del frontend no está en allow_origins, o se combinó el comodín con allow_credentials.

6

Un error inesperado devuelve la traza completa al cliente. ¿Qué falta?

El manejador de Exception que registra la traza en el log y responde 500 con un mensaje genérico.

7

¿Qué se gana al resolver el 404 en una dependencia en lugar del endpoint?

Deja de repetirse en cada endpoint del recurso y el cuerpo de la función queda reducido a la lógica propia.

8

¿Por qué el orden de registro de los middlewares importa?

El último registrado es el más externo: si mide tiempos, incluirá el trabajo de todos los demás.

from datetime import date, timedelta

from itertools import count

from app.crud import libros as crud_libros

from app.datos import buscar_socio_por_id

from app.errores import (

 LimiteDePrestamosSuperado,

 PrestamoYaDevuelto,

 RecursoNoEncontrado,

 SinEjemplaresDisponibles,

 SocioInactivo,

)

PRESTAMOS: list[dict] = []

_siguiente_id = count(1)

LIMITE_PRESTAMOS_ACTIVOS = 3

def listar(estado: str | None = None, socio_id: int | None = None) -> list[dict]:

 resultado = [_con_estado(p) for p in PRESTAMOS]

 if estado is not None:

 resultado = [p for p in resultado if p["estado"] == estado]

 if socio_id is not None:

 resultado = [p for p in resultado if p["socio_id"] == socio_id]

 return resultado

def _con_estado(prestamo: dict) -> dict:

 """Calcula el estado en el momento de la consulta, sin almacenarlo desactualizado."""

 if prestamo["fecha_devolucion_real"] is not None:

 estado = "devuelto"

 elif prestamo["fecha_devolucion_esperada"] < date.today():

 estado = "vencido"

 else:

 estado = "activo"

 return {**prestamo, "estado": estado}

def obtener_o_fallar(prestamo_id: int) -> dict:

 for prestamo in PRESTAMOS:

 if prestamo["id"] == prestamo_id:

 return _con_estado(prestamo)

 raise RecursoNoEncontrado("un préstamo", prestamo_id)

def _activos_del_socio(socio_id: int) -> int:

 return sum(

 1

 for p in PRESTAMOS

 if p["socio_id"] == socio_id and p["fecha_devolucion_real"] is None

 )

def registrar(libro_id: int, socio_id: int, dias_prestamo: int) -> dict:

 """Aplica, en orden, todas las reglas de negocio del préstamo."""

 socio = buscar_socio_por_id(socio_id)

 if socio is None:

 raise RecursoNoEncontrado("un socio", socio_id)

 if not socio["activo"]:

 raise SocioInactivo(socio_id)

 if _activos_del_socio(socio_id) >= LIMITE_PRESTAMOS_ACTIVOS:

 raise LimiteDePrestamosSuperado(socio_id, LIMITE_PRESTAMOS_ACTIVOS)

 libro = crud_libros.obtener_o_fallar(libro_id)

 if libro["ejemplares_disponibles"] <= 0:

 raise SinEjemplaresDisponibles(libro_id)

 libro["ejemplares_disponibles"] -= 1

 hoy = date.today()

 prestamo = {

 "id": next(_siguiente_id),

 "libro_id": libro_id,

 "socio_id": socio_id,

 "fecha_prestamo": hoy,

 "fecha_devolucion_esperada": hoy + timedelta(days=dias_prestamo),

 "fecha_devolucion_real": None,

 }

 PRESTAMOS.append(prestamo)

 return _con_estado(prestamo)

def registrar_devolucion(prestamo_id: int) -> dict:

 for prestamo in PRESTAMOS:

 if prestamo["id"] == prestamo_id:

 if prestamo["fecha_devolucion_real"] is not None:

 raise PrestamoYaDevuelto(prestamo_id)

 prestamo["fecha_devolucion_real"] = date.today()

 libro = crud_libros.obtener(prestamo["libro_id"])

 if libro is not None:

 libro["ejemplares_disponibles"] += 1

 return _con_estado(prestamo)

 raise RecursoNoEncontrado("un préstamo", prestamo_id)

from typing import Annotated

from fastapi import APIRouter, Path, Query, status

from app.crud import prestamos as crud_prestamos

from app.dependencias import Bibliotecario, PaginacionDep, SocioActual

from app.schemas.error import DetalleDeError

from app.schemas.prestamo import PrestamoCrear, PrestamoRespuesta

router = APIRouter(

 prefix="/prestamos",

 tags=["Préstamos"],

 responses={

 404: {"model": DetalleDeError},

 409: {"model": DetalleDeError},

 },

)

@router.get(

 "",

 response_model=list[PrestamoRespuesta],

 summary="Listar préstamos",

)

def listar_prestamos(

 solicitante: SocioActual,

 paginacion: PaginacionDep,

 estado: Annotated[

 str | None, Query(description="activo, devuelto o vencido.")

 ] = None,

):

 """Un bibliotecario ve todos los préstamos; un socio solo los suyos."""

 filtro_socio = (

 None if solicitante["rol"] == "bibliotecario" else solicitante["id"]

 )

 return paginacion.aplicar(

 crud_prestamos.listar(estado=estado, socio_id=filtro_socio)

 )

@router.post(

 "",

 response_model=PrestamoRespuesta,

 status_code=status.HTTP_201_CREATED,

 summary="Registrar un préstamo",

)

def registrar_prestamo(datos: PrestamoCrear, bibliotecario: Bibliotecario):

 return crud_prestamos.registrar(

 libro_id=datos.libro_id,

 socio_id=datos.socio_id,

 dias_prestamo=datos.dias_prestamo,

 )

@router.post(

 "/{prestamo_id}/devolucion",

 response_model=PrestamoRespuesta,

 summary="Registrar la devolución de un préstamo",

)

def registrar_devolucion(

 prestamo_id: Annotated[int, Path(ge=1)],

 bibliotecario: Bibliotecario,

):

 """La devolución es una operación de negocio, no un PATCH del préstamo."""

 return crud_prestamos.registrar_devolucion(prestamo_id)

Punto de atención

El endpoint de listado filtra por socio usando la cabecera X-Socio-Id, que cualquiera puede falsificar escribiendo otro número. Hoy es aceptable porque es un mecanismo provisional y declarado como tal; mañana, con JWT, esa identidad vendrá firmada y dejará de ser manipulable.

4. Errores comunes recopilados de las sesiones anteriores

Aplicar las reglas de negocio en desorden: comprobar los ejemplares antes que el estado del socio da un mensaje de error que no explica la causa real del rechazo.

Descontar el ejemplar antes de validar todas las reglas: si una validación posterior falla, el catálogo queda con un ejemplar perdido.

Almacenar el estado del préstamo como campo fijo: un préstamo «activo» guardado en enero sigue diciendo «activo» cuando ya venció. Se calcula en la consulta.

Modelar la devolución como PATCH /prestamos/{id}: obliga al cliente a saber qué campos tocar y permite marcar como devuelto lo que nunca se prestó.

Lanzar HTTPException desde el módulo crud en lugar de la excepción de dominio correspondiente.

Olvidar declarar 409 en responses del router: los conflictos existen pero no aparecen en /docs.

Confiar en un identificador que viaja en una cabecera sin firmar para decidir qué datos ve cada usuario.
