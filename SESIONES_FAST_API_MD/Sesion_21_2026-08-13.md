1. Objetivo de la sesión

Al finalizar esta sesión, el aprendiz será capaz de aplicar los principios REST para diseñar el conjunto de endpoints de una API a partir de un dominio de negocio, definiendo recursos, verbos HTTP, rutas y códigos de respuesta antes de escribir una sola línea de código.

2. Principios REST y diseño de recursos

Ya construyeron una API completa con Django REST Framework. Ahora vamos a cambiar de framework, y el mejor momento para hacerlo es cuando el diseño de la API está separado de la herramienta que la implementa. REST no es una librería ni un framework: es un conjunto de restricciones arquitectónicas sobre cómo un cliente y un servidor conversan a través de HTTP.

Principio

Qué significa en la práctica

Recurso

La unidad de la API es un sustantivo, no una acción: /libros, /socios, /prestamos. Nunca /crearLibro ni /obtenerSocios.

Verbo HTTP

La acción la expresa el método, no la ruta: GET consulta, POST crea, PUT reemplaza, PATCH modifica parcialmente, DELETE elimina.

Sin estado (stateless)

Cada petición viaja con todo lo necesario para ser atendida. El servidor no guarda memoria de la petición anterior; por eso la autenticación viaja en cada llamada.

Representación

El recurso vive en el servidor; lo que viaja por la red es una representación de él, normalmente en JSON.

Interfaz uniforme

Las mismas reglas aplican a todos los recursos: si /libros/{id} devuelve 404 cuando no existe, /socios/{id} también.

Código de estado

La respuesta comunica el resultado en su código, no solo en el cuerpo: 201 al crear, 204 al eliminar, 409 ante un conflicto de negocio.

Idea clave

Una API REST bien diseñada se entiende leyendo únicamente la lista de sus rutas y verbos, sin abrir el código. Si para saber qué hace un endpoint hay que leer la función que lo implementa, el diseño falló.

Equivalencia con Django REST Framework

En DRF el diseño REST venía en gran medida regalado: un ModelViewSet más un DefaultRouter generaban automáticamente las seis rutas del CRUD. En FastAPI no existe ese automatismo — cada ruta se declara explícitamente. Es más trabajo y, a la vez, más control: nada aparece en la API sin que ustedes lo hayan escrito. Por eso el diseño previo, que en DRF se podía improvisar, aquí es obligatorio.

3. Ejemplo guiado: diseño de BiblioAPI

Durante todo el bloque de FastAPI construiremos un único proyecto de forma incremental: BiblioAPI, el backend de préstamos de una biblioteca. Es un dominio nuevo, distinto al que trabajamos en Django REST Framework, para que el aprendizaje del framework no se confunda con el recuerdo del ejemplo anterior.

Reglas de negocio que la API debe hacer cumplir

Un socio no puede tener más de 3 préstamos activos de forma simultánea.

No se presta un libro cuyo número de ejemplares disponibles sea cero.

Un socio marcado como inactivo no puede solicitar préstamos.

La fecha de devolución esperada debe estar entre 1 y 30 días después de la fecha del préstamo.

El ISBN debe tener 13 dígitos y no puede repetirse entre libros.

Roles de usuario

bibliotecario

Administra el catálogo: crea, modifica y elimina libros, autores y categorías. Registra préstamos y devoluciones de cualquier socio.

N°

Elemento

Explicación

1

POST /prestamos

El verbo expresa la intención de crear; la ruta nombra la colección donde se crea. El identificador no se envía: lo asigna el servidor.

2

HTTP/1.1

Versión del protocolo. La negocia el cliente; no es algo que definamos en la API.

3

Host: localhost:8000

Servidor y puerto destino. En desarrollo apunta a uvicorn; en producción, al dominio real.

4

Content-Type: application/json

Declara el formato del cuerpo. Si se omite o es incorrecto, FastAPI responderá 422 aunque el JSON sea válido.

5

Authorization: Bearer …

Credencial que viaja en cada petición, porque REST es sin estado. Lo implementaremos el 1 de septiembre.

6

Línea en blanco

Separa las cabeceras del cuerpo. Es parte del protocolo, no un detalle de formato.

7

{ "libro_id": 7, … }

Cuerpo de la petición: solo los datos que el cliente puede decidir. Fecha, estado e identificador los calcula el servidor.

Respuesta esperada

HTTP/1.1 201 Created

Content-Type: application/json

{

 "id": 45,

 "libro_id": 7,

 "socio_id": 12,

 "fecha_prestamo": "2026-08-13",

 "fecha_devolucion_esperada": "2026-08-28",

 "fecha_devolucion_real": null,

 "estado": "activo"

}

El código 201 indica creación, no un genérico 200. El cuerpo devuelve el recurso completo tal como quedó en el servidor, incluidos los campos que el cliente no envió: así el cliente no necesita una segunda petición para conocer el identificador ni las fechas calculadas.

5. Errores comunes y cómo evitarlos

Poner verbos en la ruta: /crearPrestamo o /libros/eliminar/3. La acción la expresa el método HTTP; la ruta solo nombra el recurso.

Responder siempre 200, incluso al crear o al fallar. El código de estado es información: un cliente que recibe 200 con un mensaje de error en el cuerpo no tiene forma automática de detectar el fallo.

Devolver 500 ante un error de negocio previsible. Que un socio haya superado su límite de préstamos no es una falla del servidor: es un 409 Conflict.

Diseñar los endpoints mientras se programan. Sin la tabla recurso–verbo–ruta previa, aparecen rutas inconsistentes: /libros en plural y /socio en singular, o filtros que en un recurso son query params y en otro parte de la ruta.

Exponer en el cuerpo de creación campos que decide el servidor (id, fecha_prestamo, estado). Permitir que el cliente los envíe abre la puerta a datos incoherentes.
